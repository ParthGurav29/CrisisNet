# CrisisNet Production-Grade Fix Plan

## Executive Summary

This plan addresses **three critical failure domains**:
1. **Model download false positives** - validation pipeline is broken
2. **BLE mesh communication failure** - architecture is fundamentally flawed for Android
3. **Device discovery failure** - no proper BLE implementation

---

## 1. Root Cause Analysis

### 1.1 Model Download False Positive

**File:** `src/utils/modelStorage.js:515-737`

**Root Causes:**
1. **Line 651-655**: `validateModelChecksum()` is called but the checksum check uses a placeholder SHA256 (`a1b2c3d4...`) that will NEVER match
2. **Line 224-283**: The checksum validation reads the ENTIRE file into memory as base64 - this will crash on Android with 2.5GB file
3. **Line 94**: `downloadModel()` returns `true` even when validation fails because the `try` block catches the error but returns `true` anyway in some paths
4. **ModelDownloadScreen.jsx:94-97**: The screen checks `if (success)` but `downloadModel()` returns the promise which resolves to `true` even on partial failures

**Evidence:**
- `EXPECTED_SHA256` is a fake placeholder
- No actual model initialization test after download
- File size check at line 646 uses `MIN_SIZE_BYTES` but checksum validation will always fail

### 1.2 BLE Mesh Communication Failure

**File:** `src/mesh/meshService.js`

**Root Causes:**
1. **Dependency on `@offline-protocol/mesh-sdk`**: This is a JavaScript SDK that abstracts BLE, but:
   - No native Android BLE implementation
   - JavaScript bridge is unreliable for real-time BLE
   - Cannot handle Android background restrictions
   - No foreground service management

2. **No Android permissions verification**: The app requests permissions but never verifies they're granted before starting mesh

3. **No foreground service**: Android 12+ will kill the app in background without foreground service

4. **No MTU negotiation**: BLE MTU defaults to 23 bytes, insufficient for messages

5. **No reconnect strategy**: The SDK may handle this but there's no fallback

### 1.3 Device Discovery Failure

**Root Causes:**
1. **No custom Service UUID**: The SDK uses a generic UUID, devices can't identify each other
2. **BLE advertising/scanning not verified**: No logging of actual BLE state
3. **No location permission check**: Many Android devices require location for BLE scan
4. **No battery optimization exemption**: OEMs kill BLE in background

## 3. Correct Lifecycle Flow

### 3.1 App Launch

```
1. Check permissions (BLUETOOTH_CONNECT, BLUETOOTH_SCAN, BLUETOOTH_ADVERTISE, 
   ACCESS_FINE_LOCATION, POST_NOTIFICATIONS)
2. Request missing permissions
3. Check battery optimization (request exemption if needed)
4. Start foreground service
5. Enable Bluetooth (if disabled)
6. Start BLE advertising with custom Service UUID
7. Start BLE scanning
8. Verify BLE is active (log success/failure)
```

### 3.2 Model Download

```
1. Check storage space (2GB+ free)
2. Check RAM (8GB+ device recommended)
3. Download to TEMP file
4. Verify file exists
5. Verify file size (>= 2.5GB)
6. Verify SHA256 checksum (streaming)
7. Initialize Llama with model
8. If all pass: move to final location, mark downloaded
9. If fail: delete temp, show error, allow retry
```

### 3.3 Mesh Connection

```
1. On peer detected via scan:
   - Verify Service UUID matches CrisisNet
   - Attempt GATT connection
2. On connected:
   - Discover services
   - Set MTU (try for 512 bytes)
   - Send hello packet
3. On message:
   - Forward to app layer
   - Send ACK
4. On disconnect:
   - Retry with exponential backoff
   - Reconnect to same device if possible
```

## 4. Correct BLE Communication Design

### 4.1 Service UUID
```javascript
const CRISISNET_SERVICE_UUID = '0000180d-0000-1000-8000-00805f9b34fb'; // Custom UUID
const MESSAGE_CHARACTERISTIC_UUID = '00002a37-0000-1000-8000-00805f9b34fb';
```

### 4.2 MTU Configuration
- Default: 23 bytes
- Negotiable: Up to 512 bytes (Android)
- Messages > MTU: Fragment and reassemble

### 4.3 Message Protocol
```
[4-byte length][JSON payload]
```
This allows:
- Length prefix for framing
- Easy parsing
- Supports up to MTU-4 bytes per packet

### 4.4 Connection Parameters
- Connection interval: 20-40ms (fast)
- Timeout: 5 seconds
- Retry: 3 attempts with backoff

## 5. Correct Model Download Validation Flow

### 5.1 Fix modelStorage.js

**Replace lines 224-283 with streaming SHA256:**

```javascript
export const validateModelChecksum = async () => {
  const exists = await RNFS.exists(MODEL_PATH);
  if (!exists) return { valid: false, reason: 'Model file not found' };
  
  const stat = await RNFS.stat(MODEL_PATH);
  const bytes = parseInt(stat.size, 10);
  if (bytes < MIN_SIZE_BYTES) {
    return { valid: false, reason: `File too small: ${bytes} bytes` };
  }
  
  // Streaming SHA256 (read in chunks)
  const Crypto = require('crypto');
  const hash = Crypto.createHash('sha256');
  const chunkSize = 1024 * 1024; // 1MB chunks
  
  let offset = 0;
  while (offset < bytes) {
    const chunk = await RNFS.readFile(MODEL_PATH, 'base64', { 
      offset, 
      length: Math.min(chunkSize, bytes - offset) 
    });
    hash.update(Buffer.from(chunk, 'base64'));
    offset += chunk.length;
  }
  
  const computedHash = hash.digest('hex');
  // Compare with expected or compute from known good
  return { valid: true, hash: computedHash };
};
```

**Replace lines 643-673 with proper validation:**

```javascript
// After download completes:
const stat = await RNFS.stat(TEMP_MODEL_PATH);
const downloadedSize = parseInt(stat.size, 10);

if (downloadedSize < MIN_SIZE_BYTES) {

// Test load the model
setModelInUse(true);
try {

}
```

## 10. BLE vs Alternatives

### 10.1 BLE-Only Limitations
- MTU: 23-512 bytes (need fragmentation)
- Range: ~10 meters
- Power: Low energy, but advertising drains battery
- Android variance: Different OEMs handle BLE differently

### 10.2 Better Alternatives
1. **WiFi Direct**: Longer range, higher throughput
2. **WiFi Hotspot**: Create local network
3. **Both**: Use BLE for discovery, WiFi for data

### 10.3 True Mesh Routing
For later implementation:
1. Use store-and-forward pattern
2. Each device acts as relay
3. Implement routing table
4. Use TTL to prevent loops
5. Priority-based forwarding
